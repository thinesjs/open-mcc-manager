# Notification connectors

The queue, retry, dedupe, signing and audit are shared. A connector is therefore a
`kind` value, a payload builder and a sender — nothing else.

## The set

| Kind | Needs | Notes |
| --- | --- | --- |
| `webhook` | url, generated signing secret | The general case. HMAC-signed. |
| `telegram` | bot token, chat id, optional thread id | Reports failure inside a `200 OK`. |
| `discord` | webhook url | Rich embed rather than plain text. |
| `slack` | webhook url | Block Kit payload. The channel is fixed when the webhook is created. |
| `teams` | webhook url | Adaptive card payload. |
| `email` | smtp host, port, username, password, from, to[] | Real infrastructure; needs a mail transport. |
| `resend` | api key, from, to[] | Hosted email, one HTTP call. |
| `gotify` | server url, app token, priority | Self-hosted push. |
| `ntfy` | server url, topic, optional token, priority | Self-hosted push. |

Deliberately excluded: Mattermost, Pushover and Lark.

`discord`, `slack` and `teams` share the webhook transport but each gets its own kind
so the payload is native to the destination instead of a wall of plain text. Only the
payload builder differs; the sender is the same POST.

Only `email` needs a genuinely different transport (SMTP rather than HTTP), so it is
the one connector that cannot reuse the shared sender.

## What is NOT yet wired, despite reading as if it is

An earlier draft of this plan claimed event production was live end to end. That was
wrong, and the gap is the first thing to close:

- `isNotifyingEvent`, `problemResolvedBy` and `isFlapping` have **no production call
  sites**. They are tested primitives with nothing invoking them.
- `escalateIfStillDown` is likewise uncalled, so **`instance.disconnected` never fires**
  — the two-minute escalation that turns a brief drop into an alert does not run.
- `instance.flapping` is never produced.
- `createStatusControllerTransaction` exposes only the status repository and is
  constructed without `sendJob`, so a status event cannot enqueue anything atomically.

`statusEvent` rows *are* durably written for host reachability and observed connection
signals. Everything between "an event was recorded" and "somebody is told" is missing.

## What already exists

`notificationDestination`, `notificationSubscription`, `notification`,
`notificationDelivery` and `notificationAttempt` landed in migration 0028, all
organization-scoped with composite foreign keys and text unions.
`packages/core/src/notification/outcome.ts` already classifies a failure as
delivered, retryable or terminal, including Telegram's habit of reporting failure
inside a `200 OK`.

`statusEvent` rows are being written by the health poller and the instance observer, and
`planNotification` decides which are worth sending: `isNotifyingEvent` for problems, and
for a recovery, `problemResolvedBy` plus a look at what was last announced about that
subject. What is still missing is the wiring — `createStatusControllerTransaction` exposes
only the status repository and is built without `sendJob`, so nothing yet turns a recorded
event into a notification, a delivery and an enqueue inside one transaction.

## Webhook

Follow the Standard Webhooks specification rather than inventing headers, so that
receivers can use an off-the-shelf verifier.

| Header | Value |
| --- | --- |
| `webhook-id` | the delivery id, which is also the idempotency key |
| `webhook-timestamp` | unix seconds |
| `webhook-signature` | `v1,<base64 HMAC-SHA256>` |

The signed content is `${webhook-id}.${webhook-timestamp}.${body}` — the id and
timestamp are bound into the signature so a captured request cannot be replayed with
a fresh timestamp.

Four details that are easy to get silently wrong:

- **The HMAC key is the raw decoded bytes.** Strip `whsec_`, base64-decode the
  remainder, and sign with those bytes. Signing with the prefixed string or the base64
  text produces signatures no standard verifier accepts, with no error anywhere.
- **Serialize the body once** into UTF-8 bytes and use the same bytes for the HMAC and
  the request. Stringifying twice can differ by a byte and break verification.
- **Standard base64**, not base64url.
- **`webhook-id` is stable across every retry; `webhook-timestamp` is regenerated per
  attempt.** The id is the receiver's deduplication key, so it must never be derived
  from the attempt number or the queue's job id. It must also contain no `.`, since the
  signed string is dot-delimited.

The signing secret is **generated by us**, 32 random bytes base64-encoded with a
`whsec_` prefix, shown to the operator once at creation and on explicit rotation, and
sealed at rest. The header carries a space-delimited list so a rotation can publish
two signatures and the receiver can accept either during the changeover.

### Egress, which is the actual risk

`https` and a timeout say nothing about *where* the connection goes. Required, at
connection time rather than only at save time:

- Resolve every A/AAAA answer and reject the destination unless all are globally
  routable unicast. Loopback, RFC1918, unique-local, link-local, carrier-grade NAT,
  multicast, documentation, benchmarking, reserved and cloud metadata ranges are denied.
  Normalise IPv4, IPv6 and IPv4-mapped forms before deciding.
- **Pin the approved address into the connection.** Validating with a DNS lookup and
  then calling ordinary `fetch` leaves a rebinding window between check and connect.
  Node's fetch is Undici-based and accepts a custom dispatcher, which is the hook.
- Keep the original hostname for the `Host` header and TLS SNI while connecting to the
  pinned address, or certificate verification breaks.
- Use a per-request dispatcher so pooling cannot reuse a socket validated for something
  else.
- Never follow a redirect. Treat any 3xx as a failed delivery. The specification
  recommends not following redirects at all, and the HTTP client must not be configured
  with anything that would.
- Private targets come only from an administrator-controlled allowlist of exact hosts or
  addresses and ranges — never a per-destination "allow private" checkbox, and never a
  switch that disables the address policy wholesale. A hard-denied tier sits above the
  allowlist and cannot be opened by it: the unspecified address, link-local space, the
  known cloud metadata endpoints, multicast and reserved space.
- Plain `http` is a separate decision from reaching a private address, and is permitted
  only when every resolved answer was explicitly named by the administrator.

Request timeout 20 seconds, as a single deadline covering name resolution, connection and
the response — not a per-phase timeout that can add up to more. The response body is read
up to a small cap and discarded: we need the status, not the content.

### The secret, and rotating it

The whole URL is sealed, not just the token, because a webhook URL routinely carries a
bearer-equivalent secret in its path or query. `displayTarget` holds only a sanitised
origin.

Rotation keeps the previous key in the sealed envelope with an expiry. During the
overlap — 24 hours — both signatures are sent, space-delimited, and the receiver may
accept either. At expiry the old key is purged. A second rotation is refused while an
overlap is active unless the operator explicitly ends the current one.

`packages/core/src/security/redact.ts` redacts `whsec_` values, Telegram bot tokens both
in a URL and bare, the secret path of a Slack, Discord or Teams incoming webhook, and
Resend keys. A generic webhook URL is a secret we cannot pattern-match, so the sender
additionally strips the configured target out of any transport error before it is stored
or logged. No raw URL or provider response body may reach a stored failure reason.

## Telegram

`POST https://api.telegram.org/bot<token>/sendMessage` with `{ chat_id, text }`, and
`message_thread_id` when the destination names a topic. The text is plain, deliberately:
`parse_mode: "HTML"` would mean escaping server and bot names that an operator controls,
and a missed escape would be a formatting break at best.

The bot token is the secret and is sealed; the chat id is not secret and is the
destination's display target. Telegram answers `200` with `{"ok": false, ...}` on
failure, so the body decides the outcome, never the status line, and its
`description` is kept for the operator. `parameters.retry_after` sets the backoff on
a rate limit.

## Delivery

One pg-boss queue per **transport**, not per kind: `notification.deliver.http` for
every HTTP connector and `notification.deliver.email` for SMTP. A worker defaults to a
concurrency of one, so a slow SMTP handshake must not hold an HTTP POST behind it. A
queue per kind would be nine queues to serve two failure profiles.

### Queue setup, once, shared by both processes

`createQueue` uses `ON CONFLICT DO NOTHING`, so calling it again with different options
does **not** change an existing queue. One shared routine therefore runs before either
process sends or works a job: create the dead-letter queues first, create the delivery
queues with their full options, then call `updateQueue` for the mutable settings so an
existing queue converges, then read the effective configuration back and verify it.
**Both** processes run it at startup. The server enqueues, and pg-boss throws when a queue
does not exist, so it cannot rely on the worker having started first — they come up
independently.
Policy and partition changes cannot be altered after creation and are treated as a
versioned queue migration.

Concrete values: retry DISABLED at the queue (`retryLimit` 0, `retryBackoff` off, no maximum
delay), job expiry 5 minutes, delivery retention 14 days and dead-letter retention 30 days,
dead-letter queue `notification.deadletter`. Retrying is ours, not the queue's — see below —
and the dead-letter link stays only so an unexpected throw is still kept. The option names
must be taken from the installed pg-boss rather than assumed: an option it does not recognise
is ignored in silence, so a retention we believe we set may never take effect. Verification
means comparing every mutable option that comes back, not merely that the queue exists.

A terminal outcome dead-letters immediately rather than burning the retry budget on
something that will never succeed.

Retrying is **ours, not the queue's**. The delivery queues are created with retry disabled,
the attempt number rides in the job payload, and a retryable outcome writes the delivery
state and schedules its own replacement job in one transaction. A final failure settles the
delivery and sends it to the dead-letter queue explicitly — resolving the handler normally
would make pg-boss mark a failed job *complete*. The queue keeps its dead-letter link anyway,
so an unexpected throw is still caught.

A notifying `statusEvent` produces, inside **one transaction**: the `notification`
row (unique on `dedupeKey`), one `notificationDelivery` per enabled subscribed
destination (unique on notification+destination), and the enqueue via
`boss.send(queue, payload, { db: runner })`. If the transaction rolls back there is
no orphaned job. The job payload is `{ organizationId, deliveryId, attempt }` and nothing
else: the notification and the destination are read from the delivery row, never taken from
the job, so a malformed job cannot send one notification to another destination.

Delivery is **at least once**, never exactly once, and the UI says so. The receiver
deduplicates on `webhook-id`; Telegram offers no equivalent, so a duplicate message
remains possible if the worker crashes between sending and settling.

The worker therefore guards on stored state before sending: a delivery already `delivered`,
`failed` or `abandoned` is skipped and the replayed job simply completes. It is not
dead-lettered a second time — the dead-letter row was written in the same transaction that
settled it as failed. This covers a crash after the domain result commits but before the
queue settles.

Each attempt writes a `notificationAttempt` row. A failure records a reason on the
destination so the operator sees it without reading logs.

`Retry-After` on a webhook and `parameters.retry_after` from Telegram actually change *when*
the next attempt happens. Queue-level backoff cannot express a response-specific delay, so
the next wait is the LARGER of our own backoff and whatever the provider asked for, capped at
an hour. We never retry sooner than a provider told us to.

The enqueue must fail loudly: `boss.send` returning `null` means no job exists, and a
committed delivery with no job would never be sent. That case throws.

## Test connection

Sends a real notification of kind `test` through the same queued path, so a test
exercises exactly what production exercises. It is never a second inline
implementation.

## Settled: a failing destination stays enabled

A destination that accumulates failures stays **enabled and visibly unhealthy** rather
than auto-disabling. Automatically disabling can silently remove the only path by which
an operator would learn anything is wrong, and "enabled" does not mean an infinite retry
loop — each delivery is bounded by `retryLimit` and then dead-lettered.

One exception, because the protocol is explicit: a webhook answering **`410 Gone`** is
telling us to stop, and that destination is disabled automatically. The classifier carries
this as its own disposition, separate from an ordinary refusal that an operator can fix.

## Scope, stated plainly

This ships the nine connectors above. It **defers** Web Push and the in-dashboard read
state (`notificationRead`) that the earlier notifications plan committed to. Those are
not cancelled; they are a later phase, and the earlier plan's 90-day retention and its
rule that a notification is never deleted while a delivery is queued, retrying or held
in the dead-letter queue still stand and must be implemented with the cleanup job.

The earlier plan named an `Idempotency-Key` header; the correct header is `webhook-id`,
per the specification. That supersedes it.

## Before any of this can be trusted

- A **real rollback integration test**: send through a Kysely transaction, throw, and prove
  both the domain rows and the queue job are absent. Done — it starts a real pg-boss against
  the test database rather than a no-op double, so the guarantee is no longer a claim.
- Contracts owns `as const` arrays and schemas for destination kinds, notification kinds,
  subscription kinds, delivery states and outcomes, and the database layer is narrowed to
  match. Done: `notification.kind`, `notificationSubscription.kind` and the notification
  subject type are refined, `notificationSubscription` is registered with its narrowed table,
  and a drift test compares the migration check-constraint lists against the contracts arrays
  in both directions.
- Telegram JSON and the sealed provider config are untrusted input and are parsed under
  `packages/contracts/src/boundary/`, never in core.
- Operator-facing copy never exposes "terminal", "retryable", "dead-letter", a raw
  provider body, or a raw URL.
